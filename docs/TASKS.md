# 第一阶段学习任务：Task 0-6

> 本文件定义第一阶段的 7 个可验收学习任务。它不替代 16 章教程：章节说明完整的原理与扩展方向，第一阶段只选取建立工程判断所需的内容、示例和验收标准。逐项命令、通过条件与记录模板见 [第一阶段验收包](phase1/README.md)。

每项任务都按[任务记录卡](phase1/task-record-guide.md)保留“输入 -> 动作 -> 证据 -> 结论”；没有设备时，结论只能覆盖 CPU 对照、设计推导或模拟契约。

## 使用规则

- 每个 Task 先读指定章节，再运行对应示例，最后完成验收问题或实验记录。
- 不以阅读量作为完成条件；必须能解释一次结果、一个瓶颈或一个失败条件。
- 没有 GPU、NPU 或开发板时，先完成 CPU 和 `simulated` 路径；硬件任务保留为可选扩展，不能阻断前置学习。
- 性能数字只在同一机器、同一输入和同一测量口径下比较；教学模拟数据不代表真实设备结果。

## 第一阶段目标：建立最小异构工程判断力

第一阶段包含 **Task 0-6**。它的目标不是逐章覆盖全书、穷举平台或完成生产级系统，而是在任意一台可编译的主机上建立可复核的工程判断：

```text
识别可并行工作
    -> 用 Host 切分、提交和收口任务
    -> 映射一项 Device 工作及其内存访问
    -> 用正确性检查和时间数据解释结果
    -> 完成一次受限的优化、部署和系统设计练习
```

完成第一阶段后，学习者应能：

1. 区分数据并行、任务并行和流水线，并说明它们的同步代价。
2. 用线程池、OpenMP 或 SIMD 解释 Host 端的任务切分与局部执行效率。
3. 说明 Host 为什么要管理数据放置、异步提交和同步收口。
4. 阅读并运行 `vec_add` 或 `reduce` 的 CPU 路径；有 CUDA 环境时运行对应 CUDA 路径。
5. 完成一次受限的算子优化和一次部署契约演练，并区分模拟、正确性验证和真实设备测量。
6. 为一个小型云端或边缘场景写出设备分工、同步点、指标和风险，而非交付完整生产系统。

第一阶段不要求逐章读完第 1-16 章。第 12 章、厂商真实工具链、多设备协同、完整 LLM 服务和生产级运维属于第二阶段专题；第 4-6 项只阅读完成当前任务所需的小节。

## 第一阶段范围

| Task | 第一阶段只取用的内容 | 明确不要求 |
|---|---|---|
| 0 | 环境、构建、CPU 正确性基线 | 容器、CUDA、厂商 SDK 安装 |
| 1 | 第 1-3 章的并行模型与上限 | 并发 API 全语法与死锁排障 |
| 2 | 第 4-7 章的一个 Host 主实验与两个机制观察 | 复杂线程框架与真实多设备并行 |
| 3 | 第 7-9 章的一个基础 Device 映射 | CUDA 设备实测与全部优化技巧 |
| 4 | 第 10、13 章中的一次融合/测量练习 | 云端服务、多卡或完整注意力优化 |
| 5 | 第 11 章中的一次模拟部署契约练习 | Jetson、RK3588、昇腾的真实部署 |
| 6 | 第 14-16 章中的一个场景化设计练习 | 生产级云边系统与全书选型穷举 |

## 第二阶段入口

完成 Task 0-6 后，再按实际工作方向选择专题，而不是继续按章节线性推进。专题入口、进入条件和共用验收规则见 [第二阶段专题路线](phase2/README.md)：

- 云端 GPU：深入第 9、10、13-15 章，做 CUDA profiling、算子优化、服务吞吐与多设备协同。
- 数据中心 AI 加速器：以昇腾 910B / CANN 等真实工具链为例，补模型转换、运行时接入、实测报告和对照实验。
- 边缘 AI：先完成 Jetson Orin Nano 真实视觉流水线，再以 RK3588 等 NPU 做量化与运行时约束对照。
- 可移植性：按项目需要学习第 12 章的 OpenCL / SYCL，不作为所有学习者的共同前置。
- 系统工程：扩展第 14-16 章，加入任务图、背压、故障处理、成本与量产维护。

## 无硬件学习路径

没有 GPU、Jetson 或 NPU 开发板时，仍可完成第一阶段：Task 0-3 走 CPU 路径，Task 4-6 走模拟或设计路径。完成标准是正确性、时序与报告解释，不是复现实机加速比。

1. 执行 `ctest -L cpu`，运行 `ch04_task_pool`、`ch05_openmp_blur`、`ch06_simd_layernorm` 和 `ch09_vec_add` 的 CPU 路径。
2. 在 Task 3 为 `vec_add` 或 `reduce` 写出线程映射、内存访问和预期 GPU 瓶颈；没有 GPU 时明确记录“未进行硬件验证”。
3. 执行 `ctest -L python`，检查第11章部署报告的 `execution_mode: simulated` 与失败语义。
4. 运行 `examples/ch14_face_detection/pipeline.py --backend cpu --frames 3 --report-json /tmp/face.json`，分析队列和阶段耗时，但不把结果称为 Jetson 或 NPU 性能。

硬件到位后，只需补做对应平台的 CUDA、Jetson 或 NPU 验收；真实厂商工具链的深入接入仍放在第二阶段。

## Task 0：建立运行基线

**目标**：确认本地能构建、运行和验证最小示例，理解“正确性”和“性能”是两类不同结果。

| 项目 | 内容 |
|---|---|
| 阅读 | [环境说明](ENVIRONMENT.md)、[使用说明](USAGE.md)、第1章导读 |
| 运行 | `cmake -S . -B build`、`cmake --build build`、`ctest --test-dir build -L cpu --output-on-failure` |
| 观察 | CTest 的通过/失败、输入规模、串行参考实现与并行候选实现 |
| 产出 | 一份环境记录：系统、编译器、线程数、已用命令与测试结果 |

**完成标准**：CPU 测试全部通过；能够说明为什么性能基准不能直接替代正确性测试。

**边界**：此任务不安装 CUDA、厂商 SDK 或开发板依赖。环境不可用时先排除构建问题，不跳到后续算子优化。

参考表达见 [运行基线记录](phase1/task0-baseline-reference.md)。

## Task 1：建立并行问题模型

**目标**：把“要加速”转换为可判断的任务结构、依赖关系和收益上限。

| 项目 | 内容 |
|---|---|
| 阅读 | 按[Task 1 最小阅读清单](phase1/task-record-guide.md#最小阅读清单)完成第 1-3 章所需小节；不要求通读第 2 章的发布顺序与失败路径 |
| 实验 | 按[Task 1 验收命令](phase1/README.md#task-1并行问题模型)复用 Task 0 的 `build/` 运行 [`ch09_vec_add`](../examples/ch09_vec_add/README.md) 的 CPU 路径，并保留三组控制变量输出 |
| 重点 | Amdahl 上限、Map/Reduce、数据并行/任务并行、吞吐/延迟 |
| 产出 | 为一个自选负载写出：并行单元、共享数据、同步点和可能瓶颈 |

**完成标准**：能为 `vec_add` 选择数据并行，并说明它不适合用复杂任务图；能指出串行部分如何限制总加速比。

**不纳入本任务**：死锁排障细节、线程 API 的完整语法、CUDA 内存优化。

## Task 2：掌握 Host 控制面

**目标**：理解 CPU 在异构系统中的职责是承载任务、组织数据和控制节奏，而不是与 Device 争夺同一种计算。

| 项目 | 内容 |
|---|---|
| 阅读 | 第4-7章：线程池、OpenMP、SIMD、Host-Device 协同 |
| 实验 | 任选 `ch04_task_pool` 或 `ch05_openmp_blur` 作为主实验；阅读 `ch06_simd_layernorm` 与 `ch07_host_overlap` 的一次输出作为机制观察 |
| 重点 | 任务生命周期、共享/私有数据、循环调度、向量 lane、分块、同步收口 |
| 产出 | 一张 Host 执行记录：任务如何切分、数据在哪里、何处等待、何处可能重叠 |

**完成标准**：

1. 能解释主实验中的任务提交、执行和收口。
2. 能判断一个循环的变量应为 `shared`、`private` 或 `reduction`。
3. 能说明小批量传输和过碎同步为何会吞掉 Device 加速收益。

**不纳入本任务**：手写 CUDA kernel 调优、厂商 NPU 工具链、真实多设备并行。

参考表达见 [Host 控制面记录](phase1/task2-host-control-reference.md)。

## Task 3：完成第一个 Device 映射闭环

**目标**：将一个规则计算映射到 Device 线程层次与内存访问，建立“参考实现 -> 映射 -> 测量 -> 解释”的学习闭环。CUDA 硬件运行是可选证据，不是前置条件。

| 项目 | 内容 |
|---|---|
| 阅读 | 第8-9章；第13章的测量流程作为验收方法 |
| 实验 | `ch09_vec_add`、`ch09_reduce`；有 CUDA 时启用 `USE_CUDA=1` |
| 重点 | Host/Device 边界、grid/block/thread、全局内存访问、归约同步、CPU 参考对照 |
| 产出 | 一份算子记录：输入规模、实现、正确性结果、时间数据、首要瓶颈判断 |

**完成标准**：能画出 `vec_add` 或 `reduce` 的数据流和线程映射；能解释 CPU 对照、CUDA kernel、数据传输各自验证什么；无 GPU 时只将映射视为设计推导，并明确记录未进行硬件验证。

**基础算子验收**：选择 `vec_add` 或 `reduce`，提交一页实验记录，不要求固定加速比，但必须包含正确性结果、测量口径和瓶颈解释。

无 GPU 的参考表达见 [基础 GPU 算子记录](phase1/task3-gpu-operator-reference.md)。

## Task 4：完成一次受限算子优化

**目标**：理解优化不是只缩短 kernel，而是减少中间张量、改善复用，并用一次可复测的对照解释变化。

| 项目 | 内容 |
|---|---|
| 阅读 | 第10章、第13章；第14章大模型调度案例仅作应用语境 |
| 实验 | `ch10_fused_softmax` 的 unfused 与 fused 对照；`ch09_gemm` 和 `ch14_attention_pipeline` 只作延伸阅读 |
| 重点 | tile、带宽与算力边界、算子融合、时间线、batch、排队和端到端延迟 |
| 产出 | 一份优化前后对照：修改点、正确性、指标变化、未改善的瓶颈 |

**完成标准**：能够区分“kernel 更快”和“端到端更快”；能说明 fused softmax/attention 为什么要消除中间张量。

**边界**：不要求搭建云端服务、实现 FlashAttention 或进行多卡吞吐调优；这些属于第二阶段云端 GPU 专题。

CPU-only 的融合对照见 [受限算子优化记录](phase1/task4-optimization-reference.md)。

## Task 5：完成部署契约演练

**目标**：完成一次模拟部署演练，理解模型格式、量化、运行时和报告边界。真实设备部署属于第二阶段的硬件专题。

| 项目 | 内容 |
|---|---|
| 阅读 | 第11章；第14章案例1与第16章仅作为部署语境 |
| 实验 | 运行 `ch11_classification_infer` 的模拟报告，并主动触发一次真实模式前置条件失败 |
| 重点 | 模型格式、量化误差、后端转换、报告 schema、设备前置条件 |
| 产出 | 一份部署报告，必须包含 `execution_mode`、平台、运行时版本、模型与输入、延迟分位数、吞吐和失败条件 |

**完成标准**：模拟模式明确标识为 `simulated`；真实模式在缺少模型、SDK、设备或输入时失败而非虚构指标。

**边界**：不要求拥有 Jetson、RK3588、昇腾等平台。Jetson 视频流水线、RK3588 对照、昇腾/CANN 接入和跨平台实测属于第二阶段硬件专题。

无硬件的参考表达见 [模拟部署报告记录](phase1/task5-deployment-reference.md)。

## Task 6：完成云边端到端系统设计

**目标**：把算子、部署和 Host 调度放回一个小型场景，完成可解释的设备分工和指标设计。

| 项目 | 内容 |
|---|---|
| 阅读 | 第14-16章；第12章仅在存在跨平台约束时选读 |
| 实验 | `ch14_face_detection`、`ch14_attention_pipeline` |
| 重点 | 采集/推理/后处理流水线、任务图、队列、背压、跨设备边界、云边选型 |
| 产出 | 一个场景设计：任务图、设备分工、同步点、测量指标、风险与备选方案 |

**完成标准**：能为一个云端或边缘场景说明为何使用 CPU/GPU/NPU 的组合；能明确哪些指标是模拟、哪些来自真实设备；能提出至少一个可复测的系统改动。

**边界**：输出的是设计与小型验证，不要求部署生产服务、实现跨设备容错或覆盖全部硬件组合。

无硬件的参考表达见 [边缘视觉系统设计记录](phase1/task6-system-design-reference.md)。

## 第一阶段依赖与第二阶段分支

```text
第一阶段：Task 0 -> Task 1 -> Task 2 -> Task 3 -> Task 4 -> Task 5 -> Task 6
                                                        |          |
第二阶段：云端 GPU / 算子优化                  边缘 AI 或数据中心 AI 加速器
                                                        \-> 第12章跨平台选读（按需）
```

- 以云端 GPU 为目标：第一阶段在 Task 5 使用模拟报告完成部署语义，第二阶段再进入 CUDA profiling、服务吞吐和多设备专题。
- 以边缘 AI 为目标：第一阶段在 Task 4 完成最小融合/测量对照，Task 5 优先选择 Jetson 或模拟部署；第二阶段再比较 RK3588 等 NPU。
- 以系统/平台工程为目标：第一阶段完成 Task 6 的小型设计，第二阶段再深入第 13、15、16 章的工程约束。

## 维护规则

- 新增实验必须标注归属 Task、前置任务、硬件条件和验收输出。
- 新增章节若改变任务依赖，应同时更新本文件、[ARCHITECTURE.md](ARCHITECTURE.md)、[USAGE.md](USAGE.md) 和示例索引。
- Task 0-6 是稳定的第一阶段范围；新增平台、厂商工具链和生产级案例应优先归入第二阶段专题，不扩大第一阶段。
