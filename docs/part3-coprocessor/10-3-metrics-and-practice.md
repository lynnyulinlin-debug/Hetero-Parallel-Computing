# 10.3-10.5 指标解读与实战对照

## 10.3 关键性能指标解读

这一节的目标，不是背指标，而是把指标翻译成结论，再翻译成动作。

- **SM 占用率（occupancy）**：活跃 warp 比例，太低说明并行度不足。
- **全局内存吞吐量**：是否接近硬件带宽上限（判断带宽受限）。
- **共享内存 bank 冲突**：访问是否被串行化。
- **原子操作压力**：归约朴素版常见瓶颈，通常比普通算术更敏感。

对应的判断链条通常是：

1. 占用率低，先看线程块/寄存器/资源分配是否限制了并行度。
2. 带宽打满，先想办法减少搬运或提高复用。
3. bank 冲突高，先看数据布局和访问模式。
4. 原子压力高，先考虑分层归约或降低争用。

## 10.4 实战：用 profiler 定位矩阵乘的瓶颈并优化

- 朴素矩阵乘 → profiler 显示全局内存吞吐打满 → 引入分块平铺 → 再测验证。
- 串联第9.6节，形成"测—改—再测"闭环。

这里强调的是方法，不是某个特定 kernel 的最优写法。profiler 里看到“带宽先满”，就优先考虑数据复用和分块；看到“并行度不足”，就先查资源占用和调度策略。

## 10.5 实战补充：用 profiler 对比 vec_add 与 reduce

- `vec_add` 的时间线通常能直接看到 H2D/D2H 占比偏高，说明小批量任务被传输开销主导。
- `reduce` 的朴素版会暴露出同步与原子压力，shared 版则应减少全局争用。
- 先跑 `nsys` 看系统级时间线，再用 `ncu` 看单核函数细节，是最稳妥的分析顺序。

这两个例子之所以适合放在一起，是因为它们分别对应两种典型判断：

- `vec_add` 更容易暴露“传输占比太高”的系统级问题。
- `reduce` 更容易暴露“核内部争用太高”的局部问题。
