# 11.3 模型转换流程

NPU 部署最容易让人迷路的地方，不是模型本身，而是“框架图、导出图、量化图、板端图”之间的对应关系。最稳妥的思路是先把整个流程切成四段，再分别验证每一段的输入和输出。

## 11.3.1 从框架到 ONNX

第一步是把训练框架里的模型导出为 ONNX。

- 训练框架可能是 PyTorch、TensorFlow、JAX 或别的框架。
- ONNX 的作用是提供一个中间表示，避免把框架细节直接绑到厂商 SDK 上。
- 导出时必须确认：
  - 输入张量名
  - 输出张量名
  - 输入尺寸
  - 是否允许 dynamic batch
  - 归一化参数是否正确

这一步的目标不是“导出成功就行”，而是让后面的量化和转换有一个稳定的图输入。  
在本书的示例里，`examples/ch11_npu_deploy/01_export_onnx.py` 负责冻结这类接口信息。

## 11.3.2 从 ONNX 到量化产物

第二步是做 PTQ 或 QAT 相关准备。

- **PTQ**：先导出，再用校准集做量化。
- **QAT**：训练阶段就模拟量化误差。

对于大多数工程场景，PTQ 是第一选择，因为它接入成本低、流程清晰，适合先验证部署链路。  
如果 PTQ 后精度掉得太多，再考虑 QAT。

## 11.3.3 从量化产物到厂商格式

第三步才是厂商 SDK 真正介入的地方。

- RKNN 场景下，ONNX 会被转换成 RKNN 工件。
- 昇腾场景下，ONNX 会被转换成 OM 或对应的板端产物。
- TFLite delegate 场景下，会生成 TFLite 相关模型并交给对应运行时。

这一段最重要的原则是：**先冻结上游接口，再替换下游实现**。  
不要一边改导出图，一边改转换脚本，还一边改板端推理，否则排查问题会失控。

## 11.3.4 在板端验证

最后一步是板端推理验证。

你至少要回答四个问题：

1. 模型是否成功加载？
2. 推理是否有输出？
3. 结果是否与基线一致？
4. 延迟和吞吐是否满足目标？

本书的 `examples/ch11_npu_deploy/04_infer.py` 不是厂商 SDK 的真实实现，而是把这一步的接口、报告格式和检查项固定下来，后续接真实后端时只需要替换内部逻辑。

## 11.3.5 为什么这条流程必须按顺序走

NPU 部署最忌讳上游接口还在变、下游脚本已经开始调。  
如果你先改转换器，再改导出图，再改板端推理，排查问题时就很难分清到底是模型本身、量化参数、算子兼容，还是板端运行时出了问题。把“框架 → ONNX → 量化 → 厂商格式 → 板端验证”这个顺序固定下来，真正的意义不是机械化流程，而是让每一层问题都能在自己的边界内被定位。
