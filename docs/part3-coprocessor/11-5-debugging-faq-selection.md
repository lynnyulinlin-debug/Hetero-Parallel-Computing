# 11.6-11.9 调试、FAQ 与选型

## 11.6 性能调试

NPU 调试最常见的问题不是“算力不够”，而是“链路不对”。

### 11.6.1 先看整体，再看单点

调试时应该先回答：

- 端到端链路是否被数据搬运拖慢？
- 量化和转换是否引入了额外开销？
- 板端加载和初始化是否太重？

只有整体链路看明白了，再去看具体算子是否是瓶颈。

### 11.6.2 典型观测项

- NPU 利用率
- DMA 带宽
- 单算子耗时
- CPU 与 NPU 的同步开销
- 板端初始化与加载耗时

### 11.6.3 什么时候怀疑是数据布局问题

如果出现下面这些现象，先怀疑数据布局而不是算力：

- 推理结果有，但速度远低于预期
- 算子看似支持，但吞吐异常低
- 量化后比未量化慢很多

这种情况往往意味着输入输出布局、内存对齐或拷贝方式有问题。

## 11.7 ⚡️ 常见问题

这一节建议按“先导出、再量化、再转换、最后板端”顺序排查。

### 11.7.1 导出阶段

- checkpoint 路径是否正确？
- 输入尺寸、输入名、输出名是否一致？
- ONNX 是否能被下游工具链接受？

### 11.7.2 量化阶段

- 校准集是否代表真实分布？
- PTQ 后精度下降是否在可接受范围？
- 是否需要切换到 QAT？

### 11.7.3 转换阶段

- 后端是否支持当前模型里的算子？
- 动态 shape 是否被固定了？
- 是否有无法融合的子图？

### 11.7.4 板端验证

- 模型是否成功加载？
- 推理是否有输出？
- 结果是否和基线一致？
- 性能是否达到目标？

### 11.7.5 最常见的五个坑

1. checkpoint 能找得到，但原框架加载失败。
2. ONNX 导出了，但输入输出名和脚本不一致。
3. 校准集太少或分布偏。
4. 目标硬件不支持关键算子。
5. 量化后精度下降，但没有先排查前处理和后处理。

## 11.8 📋 产品经理视角：GPU vs NPU 选型决策表

| 维度 | GPU | NPU |
|------|-----|-----|
| 灵活性 | 高（支持新算子/动态图） | 低（算子受限） |
| 能效 | 较低 | 高 |
| 开发周期 | 短（生态成熟） | 长（转换/调试成本） |
| 适用 | 训练、多变模型、原型 | 固定模型量产、边缘端 |

对产品经理来说，判断标准不是“哪个更先进”，而是：

- 需求是否经常变
- 是否有明确硬件约束
- 是否要量产和控功耗
- 团队是否有足够人力处理转换和调试

## 11.9 小结

这一章最重要的结论有四个：

1. NPU 用数据流换能效，牺牲灵活性，与 GPU 的 SIMT 互补。
2. 部署流程以 ONNX 为枢纽：框架 → ONNX → 厂商格式 → 板端验证。
3. 量化是 NPU 部署的关键，校准集质量直接影响最终效果。
4. 真实工程里最常见的问题往往不是“算力不够”，而是“接口、布局、算子、后处理”没对齐。
5. 这章的脚手架是为了帮助你以后接真实后端时保留稳定边界。
