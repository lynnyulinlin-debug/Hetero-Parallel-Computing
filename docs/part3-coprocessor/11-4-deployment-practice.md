# 11.5 部署实战

这部分不要只理解成“脚本演示”，它实际上是在说明 NPU 部署工程应该怎么组织。

## 11.5.1 分类模型接入

分类模型适合作为起步样例，原因很简单：输入输出最简单，最容易验证导出、量化和推理三段是否一致。

你可以把它理解成一个四步验证链：

1. 确认 checkpoint 能被原框架加载。
2. 确认 ONNX 能正确导出。
3. 确认校准集能被量化脚本读取。
4. 确认推理报告能生成。

在本书示例里，`resnet18_example.md` 就是分类模型的标准起步样例。

## 11.5.2 检测模型接入

检测模型比分类模型更接近真实工程，也更容易出问题。

原因有三个：

- 输入尺寸通常更大。
- 后处理更复杂。
- 算子兼容性问题更容易暴露。

所以检测模型接入时，除了导出、量化、推理，还要额外确认：

- NMS 是否在板端还是 CPU 侧执行
- 框坐标是否与预处理一致
- 阈值和精度之间的平衡是否合理

在本书示例里，`detection_example.md` 就是对应的检测模型起步样例。

## 11.5.3 真实模型接入规范

真正的工程接入，建议按固定目录约定组织：

- `checkpoints/`：训练权重或原始 checkpoint
- `data/calib/`：校准集和清单
- `data/test/`：测试集和清单
- `artifacts/`：导出、量化和推理产物

真实接入流程建议先看 `examples/ch11_npu_deploy/models/integration_guide.md`，它的作用就是把“新模型怎么接进来”讲成一套顺序固定、职责清楚的规范。

## 11.5.4 本章脚手架如何理解

本书的 `examples/ch11_npu_deploy/` 不是完整厂商实现，而是把部署链路拆成可维护的阶段：

- `01_export_onnx.py`：冻结模型与输入输出接口
- `02_quantize.py`：冻结校准集、后端和量化参数
- `03_convert_*`：冻结厂商格式转换入口
- `04_infer.py`：冻结板端验证和报告格式

换句话说，这个示例的重点不是“已经替你做完部署”，而是“以后接真实 SDK 时不用推倒重来”。

## 11.5.5 什么时候应该先看模板，再接真实后端

如果你的目标是先把一个模型接进 NPU 链路，最合适的做法不是一上来就啃厂商 SDK 的全部细节，而是先按本章模板固定四件事：输入输出接口、校准集和测试集目录、导出/量化/转换/推理的命令边界，以及哪些地方以后会被厂商实现替换。这样做的好处是，等你真正去接 RKNN、昇腾或其他后端时，很多问题已经在模板层被归好类了。
