# Task 1 参考记录：`vec_add` 的并行问题模型

> 本记录示范第一阶段 Task 1 应如何表达问题模型。它基于维护工作站在 2026-10-21 的 CPU-only 运行，不是跨机器性能基准，也不包含 GPU 硬件测量。

## 负载与执行条件

```text
y[i] = a[i] + b[i], 0 <= i < 4099
```

执行命令：

```bash
./build/ch09_vec_add 4099
```

环境摘要：Linux x86_64、GCC 13.1、OpenMP、32 个逻辑核心；未设置 `OMP_NUM_THREADS`。数值校验为 `PASS`，CUDA 未编译。

## 问题模型

| 项目 | 判断 |
|---|---|
| 并行单元 | 单个下标 `i` 的一次加法 |
| 读数据 | `a[i]`、`b[i]`，只读且可被所有工作线程共享访问 |
| 写数据 | `y[i]`，每个单元只写自己唯一的下标 |
| 单元依赖 | 无跨下标依赖，不需要归约或任务图 |
| 合法拆分 | 连续下标区间分配给不同线程，或映射到 GPU thread |
| 同步点 | 并行循环结束后，再验证或消费 `y` |

因此 `vec_add` 是数据并行的最小例子：工作规则相同，数据分片不同。它不需要复杂任务图；引入生产者-消费者队列只会增加调度成本而不消除任何真实依赖。

## 瓶颈假设

每个元素至少包含两次读取和一次写入，计算只有一次加法。大规模时首先检查内存带宽、访问连续性和 Host-Device 搬运，而不是把它误判为计算受限算子。

本次输入为非对齐的小规模 `4099`，串行中位数约 `0.003 ms`，OpenMP 中位数约 `7.694 ms`。这个结果只说明在线程创建/调度和计时开销相对于工作量很大时，并行候选实现可能更慢；它不能推出 OpenMP、CPU 或 GPU 的一般性能结论。

若迁移到 GPU，还必须单独测量：

1. Host 到 Device 的输入传输。
2. kernel 执行。
3. Device 到 Host 的结果回读。

小输入下，传输与 launch 的固定成本可能大于 kernel 收益。没有可用 GPU 时，报告必须写明“未进行 GPU 硬件验证”。

## Task 1 结论

- 该负载适合数据并行。
- 共享的是只读输入，不共享可竞争的输出位置。
- 正确性由串行参考和数组校验确认；性能仍需按输入规模与测量口径单独判断。
