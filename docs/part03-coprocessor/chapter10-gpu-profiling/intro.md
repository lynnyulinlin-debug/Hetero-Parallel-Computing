# 第10章 GPU 性能分析与云端视角

> 第9章解决的是“怎么写”，第10章解决的是“怎么知道自己写得对不对、快不快”。从这里开始，优化不再靠经验猜测，而是靠时间线、指标和复测把瓶颈一层层拆出来。

第10章的机制核心，不是记住两个工具的名字，而是建立一条稳定的诊断路径：先看系统时间线，再看单核指标，最后回到代码修改和复测。云端高吞吐服务还要把 batch、排队和多设备利用率放回同一条时间线判断。只要这条路径清楚，后面的优化就不会靠猜。

本章的工具和指标以 CUDA/GPU 为对象；NPU 的厂商 profiler 可以沿用“先时间线、后局部指标、再复测”的诊断顺序，但不能直接照搬 Nsight 的指标名称或阈值。

本章分成三个部分：

1. [10.1 时间线分析：Nsight Systems](01-timeline-analysis.md)
2. [10.2 内核指令级分析：Nsight Compute](02-ncu-analysis.md)
3. [10.3-10.5 指标解读与实战对照](03-metrics-and-practice.md)

## 语境与实验

第10章最适合放进“先写出 CUDA，再用 profiler 验证”的语境里读。比如：

- 系统时间线里，CPU 和 GPU 是否真的有重叠。
- 核函数内部，是并行度不够、带宽不足，还是同步/原子太多。
- 同一个任务改动前后，性能差异到底来自哪里。
- 云端服务吞吐下降时，问题来自单个 kernel、Host 供给，还是请求排队。

最小实验可以直接沿用第9章的案例：

1. 先用 `nsys` 看 `examples/ch09_vec_add`，确认传输和计算是否重叠。
2. 再用 `ncu` 看 `examples/ch09_reduce`，对比朴素版和共享内存版的指标。
3. 把时间线和指标结果对应起来，验证你对瓶颈的判断是否一致。

这个实验的目的，是让读者把“优化”从猜测变成可验证流程。

### 观察点

- 时间线先告诉你时间花在哪，指标再告诉你为什么慢。
- `nsys` 适合看全局节奏，`ncu` 适合看局部细节。
- 优化前后都要复测，否则改动只是感觉上的改进。

## 本章要点

1. 优化前先用时间线工具定位时间花在哪。
2. 占用率、内存吞吐、bank 冲突是最常用的三个诊断指标。
3. profiler 驱动的"测—改—验证"闭环是可靠优化的唯一正道。
4. Nsight Systems 负责看系统级节奏，Nsight Compute 负责看单核函数内部细节。
5. 云端场景还要同时观察 batch、排队和设备利用率，不能只看单个 kernel 的最优时间。

## 本章小结

第10章的重点不是工具本身，而是诊断顺序：先用时间线看全局，再用 profiler 看局部，最后把结论带回代码验证。这个闭环一旦建立，后面的优化就会从经验猜测变成可重复的方法。
