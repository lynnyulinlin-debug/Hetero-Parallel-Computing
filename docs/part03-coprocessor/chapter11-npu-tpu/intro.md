# 第11章 AI 加速器与部署链路

> 第11章从 GPU 主线转向 AI 加速器部署。你会看到 NPU 类设备为什么更强调固定图、低精度和能效，也会看到“模型 → 转换 → 量化 → 设备验证”为什么必须按顺序拆开。TPU 仅作为同类设计取向的对照，不是本书的部署主线。

本章分成五个部分：

1. [11.1-11.2 硬件特点与设计哲学](01-hardware-and-differences.md)
2. [11.3 模型转换流程](02-conversion-pipeline.md)
3. [11.4 量化原理](03-quantization.md)
4. [11.5 部署实战](04-deployment-practice.md)
5. [11.6-11.9 调试、FAQ 与选型](05-debugging-faq-selection.md)

第一次学习先看 [examples/ch11_classification_infer](../../../examples/ch11_classification_infer/README.md)：它把图像分类的导出、量化、转换和推理拆成可运行闭环。再对照 [examples/ch11_npu_deploy](../../../examples/ch11_npu_deploy/README.md)，理解如何冻结接入边界、目录约定和检查项。后者是教学脚手架，不是任何厂商 SDK 的完整产品级实现。

先建立硬件差异，再看转换与量化，最后收束到部署、调试和选型，这是第11章的阅读顺序。

## 语境与实验

第11章最适合放进“固定模型部署到设备”的语境里读：它既适用于 RK3588 一类边缘 SoC，也适用于昇腾等 AI 加速器的运行时与工具链思路。具体厂商接口必须回到真实 SDK 验证。

典型场景包括：

- 分类模型或检测模型在板端推理。
- 模型需要量化、转换和适配厂商 SDK。
- 设备功耗、体积和长期稳定性比峰值性能更重要。

最小实验先完成单模型闭环，再理解脚手架中的接入边界，而不是一开始就追求真实板卡：

1. 运行 `examples/ch11_classification_infer`，把导出、量化、转换和推理报告对应起来。
2. 对照 `examples/ch11_npu_deploy/01_export_onnx.py` 和 `04_infer.py`，看输入输出接口如何冻结。
3. 想一想模型输入尺寸、算子或后处理频繁变化时，为什么会让 NPU 部署成本上升。

这个实验的目的，是让读者先形成“部署链路”的概念，而不是一开始就被厂商工具链淹没。

### 观察点

- 模型一旦固定，转换和量化的边界就比训练阶段更重要。
- 校准集、算子兼容和板端验证，往往比单点算力更影响部署结果。
- NPU 适合稳定、重复、能效敏感的场景，不适合频繁变化的模型链路。

## 本章小结

第11章的任务不是教你“如何把任意模型塞进某个 NPU”，而是把 NPU 的硬件特点、转换流程、量化约束和调试边界讲成一条完整链路。先把这条链路看懂，再去接真实厂商 SDK，排错成本会低很多。
