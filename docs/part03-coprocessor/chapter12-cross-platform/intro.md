# 第12章 跨平台编程模型（选读）

> 只有当项目必须覆盖多个硬件后端时才进入本章。目标平台已明确为 NVIDIA CUDA、Jetson TensorRT、昇腾/CANN 或某个 NPU SDK 时，先走对应主线；不要为了“通用”额外引入一层尚无收益的抽象。

本章回答的不是“OpenCL、SYCL 是否替代 CUDA”，而是：统一 Host 接口和设备代码后，团队能得到什么复用，又必须承担什么运行时、调试和调优成本。

## 先做进入判断

满足下列任一条件，再继续读本章：

- 产品必须支持两家或以上硬件后端，且这个约束已写入交付范围。
- 后端尚未确定，需要先保留模型或算子的迁移空间。
- 团队愿意维护跨后端构建、测试和性能差异。

若以上都不满足，可跳过本章，直接从第11章进入第13章。可移植性不是免费性能，也不会抹平 GPU、NPU 或不同运行时的差异。

## 本章只建立一条 Host 流程

```text
platform -> device -> context -> queue -> program -> kernel -> buffer -> enqueue -> readback
```

它与 CUDA 的相似点是：Host 都要选择设备、准备内存、提交工作和收口结果。差别是：OpenCL/SYCL 把后端选择和运行时对象暴露为更通用的接口，因此可移植性增加，也增加了适配和测量责任。

| 约束 | 默认选择 | 本章提供的价值 |
|---|---|---|
| NVIDIA 目标明确，追求成熟调优 | CUDA | 用 OpenCL/SYCL 作为对照，不替换主线 |
| Jetson 单设备部署 | CUDA / TensorRT | 识别跨平台抽象为何不是首要问题 |
| 昇腾或其他固定 NPU 后端 | 厂商运行时 | 理解接口层与真实工具链仍有距离 |
| 多后端交付已确定 | OpenCL 或 SYCL 评估 | 比较可移植性收益与维护成本 |

## 阅读与产出

1. [12.1](01-opencl-standard.md) 和 [12.2](02-opencl-host-runtime.md)：理解开放运行时的对象边界。
2. [12.3](03-minimal-flow.md)：把 Host 流程映射到已有 `vec_add` 的“准备、提交、回读”。
3. [12.4](04-sycl.md) 和 [12.5-12.6](05-comparison-selection.md)：只在确有多后端需求时比较工程取舍。

本章的最小产出是一页选型记录：目标后端、必须复用的代码边界、预计维护成本和不采用开放标准的理由。没有稳定多后端需求时，结论“继续使用主线工具”同样是正确结果。

**小结**
第12章只解释可移植性的条件与代价，不新增一条必须掌握的编程主线。下一章回到所有后端共同需要的测量方法：先固定口径，再解释瓶颈。
