# 7.2 异步提交与同步收口

异步的价值不在于“让调用立刻返回”，而在于把提交、Device 执行和 Host 等待拆开。只有这三段之间存在可做的独立工作时，异步才可能改善端到端吞吐。

## 提交不等于完成

Host 向 Device 提交传输或 kernel 后，通常只表示工作进入队列：

```text
Host submit -> Device queue -> transfer / kernel -> completion event -> Host consumes result
```

在 completion event 之前，Host 不能假定结果已可读，也不能复用仍被传输操作引用的缓冲区。事件、流同步和显式等待的作用，都是把“何时完成”变成可检查的程序边界。

## 同步点应该服务数据依赖

同步不是越少越好，而是应该只出现在结果真正被下一阶段消费的位置：

- 后处理必须读取推理结果时，等待推理完成。
- 准备下一批输入时，不必等待上一批的无关后处理。
- 复用 Host 或 Device 缓冲区前，必须等待使用它的传输或 kernel 完成。

过早同步会把流水线重新串行化；缺少同步会形成数据竞争、读取旧结果或覆盖在途数据。第9章的 stream 和 event 会给出 CUDA 的具体接口，本节先固定其时序含义。

## 最小排查顺序

当异步版本结果错误或没有速度收益时，先检查：

1. 输入和输出缓冲区是否在完成前被复用。
2. 结果读取前是否有与数据依赖对应的同步点。
3. Host 在等待期间是否有独立工作可执行。
4. 计时是否覆盖了真正的端到端路径，而不只是提交调用。

**小结**
异步提交必须配合明确的完成条件和缓冲区所有权。下一节把这一时序模型放进传输路径，观察分块、多 stream 和数据驻留如何让传输与计算重叠。
