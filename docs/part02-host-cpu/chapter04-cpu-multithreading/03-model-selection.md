# 4.3 线程池与 OpenMP 的选择边界

线程池和 OpenMP 都会使用线程，但它们解决的不是同一类工作。选择前先看工作形态，而不是先比较 API 多少。

| 工作形态 | 优先模型 | 主要原因 |
|---|---|---|
| 不规则任务、队列、关闭协议、请求生命周期 | 线程池 | 任务提交、等待、取消和退出边界需要显式控制 |
| 规则循环、固定迭代空间、少量共享状态 | OpenMP | 运行时可接管线程团队、工作划分和汇合 |
| 规则热点循环的单核吞吐 | SIMD / 自动向量化 | 先改善每个线程内的 lane 利用率 |
| 既有阶段队列又有规则计算 | 组合使用 | 线程池或 Host 线程负责阶段控制，循环内部用 OpenMP 或 SIMD |

这不是抽象层级高低的比较。线程池提供任务生命周期控制，OpenMP 提供循环工作划分；它们可以出现在同一个系统的不同位置。

## 用已有实验建立边界

不要求把 `vec_add` 手工重写为 pthread。直接比较本书已有的两个实验即可：

- [ch04_task_pool](../../../examples/ch04_task_pool/README.md)：观察 `chunk`、队列和工作线程如何影响任务生命周期。
- [ch05_openmp_blur](../../../examples/ch05_openmp_blur/README.md)：观察循环分块、变量作用域和调度策略如何影响规则计算。

记录时只回答：当前负载是“很多独立任务”还是“一个规则循环”；谁负责任务提交与关闭；运行时是否需要显式表达队列与等待。

**小结**
线程池适合显式的任务生命周期，OpenMP 适合规则循环的工作划分。先按工作形态选择，再考虑实现复杂度和性能测量。
