# 案例3：RK3588 + RV1828 的异构视觉方案

这一案例面向边缘视觉系统：前端摄像头模组负责采集和前处理，主控板负责推理、后处理和业务决策。它的重点不是单点性能，而是完整链路如何拆分到不同硬件上，并通过流水线同时控制吞吐和延迟。这里回答的是“整条视觉链路怎么分工才最稳妥、最省资源、最容易维护”。

## RK3588 + RV1828 系统架构如何体现异构并行

从架构上看，核心不是“有两颗芯片”，而是不同硬件做不同阶段的活。`RV1828` 负责采集、ISP、编码或前置预处理，`RK3588 CPU` 负责控制流、任务调度、后处理和业务逻辑，`RK3588 NPU` 负责主模型推理，`RK3588 GPU` 负责显示、叠框或图像辅助处理。这样的分工体现的是异构性：不同单元能力不同，但协同完成同一条业务链路。  
从系统设计看，它就是一个典型的“采集侧负责把数据送进来、计算侧负责把结果算出来、显示侧负责把结果呈现出去”的三层结构。这个结构在边缘视觉里尤其重要，因为它直接决定了功耗、时延和维护复杂度。

架构图采用“采集侧 + 计算侧 + 显示侧”的三层结构。图注可写成：`RV1828 负责前端采集，RK3588 负责推理与业务控制，GPU 负责显示`。

## 从摄像头到推理的异构流水线

从执行流程上看，这是一条标准的异构流水线：摄像头或视频源进入采集侧，采集侧完成解码或前处理，结果送入 RK3588 的 NPU 做推理，CPU 再完成后处理和决策，最后由 GPU 或显示单元负责可视化。它体现的是流水并行，因为同一时刻不同帧会停留在不同阶段。  
这类方案真正的价值在于，数据流一旦被拆成阶段，系统就有机会把“采集下一帧”“处理上一帧”“显示更早的一帧”同时进行，从而把串行等待变成重叠执行。

图标出“摄像头 → 采集/解码 → 推理 → 后处理 → 显示”以及阶段之间的队列。图注可写成：`同一时刻不同帧分别停留在采集、推理、后处理三个阶段`。

## RK3588 + RV1828 的任务划分图

任务图建议画成“来源层 / 计算层 / 输出层”三层：来源层包括摄像头、视频文件和 RTSP 流，计算层包括 RV1828 采集与前处理、RK3588 NPU 推理和 CPU 后处理，输出层包括叠框、渲染、告警和上传。  
这样画的好处是，读者一眼就能看出哪些是输入边界，哪些是计算边界，哪些是业务输出边界。对于边缘系统来说，这三个边界如果画不清，后续接调度、接监控、接部署时都会乱。

任务图可直接写成下面这种文字版结构：

```text
camera/video
    |
    v
RV1828 capture + ISP
    |
    v
RK3588 queue --> RK3588 NPU infer --> CPU postprocess --> display/upload
```

- 图里明确两个关键点：哪些阶段是顺序依赖，哪些阶段可以重叠；哪些阶段跨设备，哪些阶段留在同一设备上。
- 图注可写成：`从来源层到输出层的任务划分图，强调跨设备边界与队列解耦点`。

## 这类方案要补什么信息

如果这类边缘视觉方案以后要扩成完整工程，通常还要补三类信息：

1. 摄像头型号、接口和帧率。
2. NPU 模型输入尺寸和后处理方式。
3. 推理结果如何接业务系统或显示系统。

案例3要讲完整的链路：数据从哪里来、算在哪里、结果送到哪里去。把这三段交代清楚，异构并行在真实工程里才会具体起来。
