# 案例1：实时视频流人脸检测

## 问题是什么

案例1处理的是最典型的边缘视觉问题：视频流不断进来，系统要实时检测人脸，并把结果叠到画面上。难点不在“能不能跑一帧”，而在“能否持续、稳定、低延迟地跑很多帧”。

对这类任务，单看推理算子没有意义，因为真正的瓶颈往往在采集、解码、后处理、队列阻塞和显示叠框这些环节。

## 系统结构

流水线写成：

**CPU 采集+解码 → GPU/NPU 推理 → CPU 后处理（NMS、绘框）**

当前仓库的实现对应 [`examples/ch14_face_detection/`](../../examples/ch14_face_detection/README.md)，并提供下面这些阶段：

- `pipeline.py`：串联整个流水线，负责线程、队列和指标统计。
- `stages/capture_decode.py`：采集与解码入口，当前版本支持模拟帧、文件列表、摄像头和流媒体标签。
- `stages/infer_cpu.py` / `infer_gpu.py` / `infer_npu.py`：三种推理后端。
- `stages/postprocess.py`：后处理，模拟 NMS 和绘框结果。

## 为什么队列是核心

这个案例最重要的不是“哪一段更快”，而是“如何不让某一段把整条链路拖死”。流水线里用队列把阶段隔开。

这样有三个好处：

1. 采集和推理可以解耦。
2. 推理和后处理可以重叠。
3. 任何一段变慢时，队列长度会先暴露出问题。

因此，第14章里最值得观察的指标不是单点延迟，而是：

- 端到端帧率
- `capture_q_max`
- `infer_q_max`
- 各阶段平均耗时

## 怎么看当前骨架

当前骨架使用模拟结果，但它已经把工程接口固定下来。比如：

- `--source simulated`：无硬件回退
- `--source list`：来源清单模式
- `--source camera`：单摄像头模式
- `--source stream`：单网络流模式

后续接入真实视频解码器时，只需要替换 `capture_decode.py`，不必改 `pipeline.py` 的结构。

## 观察重点

运行当前骨架时，先看：

- 后端从 `cpu` 切到 `gpu` / `npu` 后，吞吐是否变化
- 队列是不是持续积压
- 后处理是否成为新的瓶颈
- 输入模式切换后，CLI 和输出格式是否保持稳定

## 图怎么画

图可以画成三级流水线：

```text
camera/video
    |
    v
capture/decode --> infer --> postprocess --> display
```

图注可写成：

`同一时刻不同帧分别停留在采集、推理、后处理三个阶段`

## 小结

案例1的价值在于，它把“异构系统的协同”变成了可观察的流水线。你不再是单独看 GPU 或 NPU，而是看整条链路是否健康。
