# 第14章 云边端到端案例

> 第14章把第13章的方法论落到云端和边缘端的真实系统里，重点看 CPU、GPU、NPU 如何在一条流水线里协同。这里不追求单设备极限，而是看“采集、推理、后处理、调度、显示”怎样组织成可维护的端到端系统。

这一章的作用，是把前面讲过的“先测、再判因、再优化、再验证”变成真实场景中的分工图。案例2代表云端 GPU 或数据中心 AI 加速器的请求和批次调度；案例1、案例3代表边缘端的输入流、设备边界和功耗约束。

如果你想先看配套实验，可以先打开 [examples/ch14_face_detection](../../../examples/ch14_face_detection/README.md) 和 [examples/ch14_attention_pipeline](../../../examples/ch14_attention_pipeline/README.md)。前者对应视频流流水线，后者对应 FlashAttention 风格的注意力流水线。

## 这一章怎么读

阅读顺序：

1. [案例1：实时视频流人脸检测](01-face-detection.md)
2. [案例2：大模型推理的异构调度](02-llm-scheduling.md)
3. [案例3：RK3588 + RV1828 的异构视觉方案](03-rk3588-rv1828.md)

建议先看案例1，再看案例3，最后回到案例2。这样能先建立“单流水线”和“多设备边界”的直觉，再看大模型调度会更顺。

## 语境与实验

第14章最适合放进“把多个设备串成一条业务流水线”的语境里读。比如：

- 实时视频流里，采集、推理、后处理要持续重叠。
- 大模型推理里，预处理、推理和结果汇聚要分阶段组织。
- 双芯片视觉方案里，采集侧、计算侧和显示侧要明确分工。

最小实验可以围绕本书的案例骨架做：

1. 先跑案例1，看 `capture_q_max`、`infer_q_max` 和端到端帧率。
2. 再看案例2，思考 CPU 预处理和多 GPU 推理如何拆分请求。
3. 最后看案例3，确认跨设备边界如何影响吞吐、延迟和维护复杂度。

这个实验的目的，是让读者把“系统协同”看成可观察的流水线，而不是一串分散的设备名。

### 观察点

- 队列长度往往比单点速度更能暴露瓶颈。
- 后端切换不应该改整条图，主要改的是某个节点实现。
- 真实系统里，阶段衔接和数据搬运经常比单设备峰值更重要。

## 统一写法

每个案例都按同一模板写：

1. 问题是什么。
2. 系统怎么分工。
3. 数据怎么流动。
4. 指标怎么看。
5. 图应该怎么画。
6. 现实工程里最容易出什么问题。

这样无论先看哪个案例，都能快速定位它在整本书中的位置。它们不是独立故事，而是同一套方法在不同场景里的三种落点。

## 本章要点

1. 真实系统是多设备流水线，瓶颈多在阶段衔接与数据搬运。
2. 可切换后端让 GPU/NPU 选型成为工程参数。
3. 队列长度和阶段均值耗时是判断流水线健康度的最小观测集。
4. 设计型案例和可运行案例应该分层描述，避免承诺与现状不一致。

## 本章小结

第14章的作用，是把 CPU、GPU 和 NPU 放进同一条真实流水线里看协同，而不是单独看某个设备的峰值。只要读者能从这里看懂阶段分工、队列边界和后端切换，后面的系统协同和选型就会更自然。
