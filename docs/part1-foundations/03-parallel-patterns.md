# 第3章 并行模式入门

> 这一章解决什么问题：掌握一套描述并行计算的通用词汇，后续 CPU/GPU/NPU 章节都会反复用到这些模式。

沿着前两章往上看，本章把实现机制整理成 Map/Reduce、数据并行、任务并行和流水并行这些可复用的描述方式。一个并行程序可以先被翻译成“它属于哪种模式、为什么这样拆、适合哪类硬件”。

本章的重点不是记住术语本身，而是建立“用模式看系统”的习惯：同一个问题，既可以从线程和锁看，也可以从 Map/Reduce、任务并行、流水并行看。后者更抽象，也更适合跨章节复用。

## 3.1 基本并行模式

- **Map（映射）**：对每个元素独立施加同一操作（向量加法就是 Map）。
- **Reduce（归约）**：将一组值合并为一个（求和、求最大）。
- **Scatter/Gather**：按索引分散/收集数据。

## 3.2 任务并行 vs 数据并行

- **数据并行**：同一操作作用于大量数据（GPU 的主场）。
- **任务并行**：不同任务并发执行（CPU 流水线、异步阶段）。

这两类并不是互斥的。实际系统里，最常见的是“外层任务并行、内层数据并行”：例如视频流系统里，采集、推理、后处理是任务并行，而每个推理阶段内部又可能是数据并行。

### 3.2.1 组合关系比分类更重要

很多真实系统不是“纯任务并行”或“纯数据并行”，而是两者叠加：

- 上层任务并行负责阶段划分和节奏控制。
- 下层数据并行负责加速单个阶段内部的大量相似计算。

这也是为什么读第7章和第14章时，经常会看到“流水 + 任务 + 数据”混合出现。第3章先把这种组合关系讲清楚，后面才不会把并行当成单一标签。

## 3.3 吞吐量 vs 延迟（📋 产品经理重点）

- **延迟**：单个请求多快完成。**吞吐量**：单位时间处理多少。
- 加速器优化吞吐，常以牺牲单次延迟为代价；选型时要分清你真正要的是哪一个。

## 3.4 怎么把模式翻译成硬件选择

当你把一个问题写成模式以后，下一步不是立刻选设备，而是先看它的主导特征：

- **Map 为主**：通常更适合大量相似计算，GPU 往往更自然。
- **Reduce 为主**：更关注归约代价、同步和中间结果合并。
- **任务并行为主**：更适合 CPU 侧编排、线程池和流水阶段。
- **流水并行为主**：更适合视频、推理链路、边缘多阶段系统。

这不是硬规则，而是帮助你快速判断“哪类硬件更顺手”的经验框架。第8章开始进入 GPU/NPU 主线时，这种判断会反复出现。

## 3.5 本章在全书中的作用

第3章提供了一套贯穿全书的翻译层：

- 第1章告诉你为什么要并行。
- 第2章告诉你并行在系统底层怎么发生。
- 第3章告诉你这些机制通常可以被抽象成什么模式。
- 第4-7章把这些模式落回 CPU 侧实现。
- 第8-16章把这些模式继续推广到 GPU、NPU 和完整系统。

所以，第3章不是前言后的补充阅读，而是后续所有章节的共同语言。

**本章要点**
1. Map/Reduce/Scatter/Gather 是描述并行计算的通用积木。
2. 数据并行偏 GPU，任务并行偏 CPU 流水线。
3. 📋 吞吐与延迟是不同目标，决定硬件与架构选择。
