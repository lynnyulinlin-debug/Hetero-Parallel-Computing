# 第1章 为什么需要并行计算

> 这一章解决什么问题：理解并行计算为何从"可选优化"变成"必选项"，以及加速的理论上限在哪里。

当单核频率增长开始逼近功耗墙，程序性能就不再能依赖硬件自动提升。这个时候，决定系统能否继续变快的，就不只是“更快的 CPU”，而是“能不能把问题拆开、让更多执行单元一起工作”。因此，这一章先交代并行为什么成了必选项，再解释它能带来什么，以及它为什么不可能无限加速。

## 1.1 摩尔定律放缓与多核时代

- 单核频率提升触及功耗墙，性能增长转向"核数增加"。
- 免费午餐结束：串行程序不再随新硬件自动变快。

## 1.2 Amdahl 定律与 Gustafson 定律

- **Amdahl 定律**：固定问题规模下，串行部分决定加速上限。
- **Gustafson 定律**：问题规模随算力增长时，可扩展性更乐观。
- 〔图占位：不同串行占比下的加速比上限曲线〕
- 📋 这两条定律是判断"值不值得并行化"的第一把尺子。

## 1.3 并行计算的应用场景

科学计算、AI 训练/推理、图形渲染、大规模数据处理。各场景的并行特征对比。

## 1.4 并行计算是什么，如何实现

并行计算的核心思想，是把一个原本要顺序完成的任务拆成多个可以同时推进的部分，让多个执行单元在同一时间做不同的工作，从而提高吞吐、降低总耗时，或者改善响应延迟。

它解决的问题很直接：当单核频率、单设备带宽、单线程效率都不再足以继续线性提升性能时，就必须把任务分给多个执行单元一起做。

这一章回答“为什么需要并行”和“并行是什么”；第2章回答“并行在操作系统里怎么落地”；第3章回答“并行通常用哪些模式来描述”。

### 1.4.1 并行形式：数据、任务、流水与混合

- **数据并行**：同一段操作作用于不同数据。例如向量加法、图像批量处理。
- **任务并行**：不同执行单元做不同类型的工作。例如一个线程读数据，一个线程推理，一个线程后处理。
- **流水并行**：同一时刻，不同数据处在不同阶段。例如视频流里，A 帧在推理，B 帧在后处理，C 帧在采集。
- **混合并行**：实际系统里最常见，同时结合数据并行、任务并行和流水并行。

### 1.4.2 并行实现：拆分、调度、同步与均衡

并行计算不是自动发生的，通常要经过下面几层配合：

1. **任务拆分**
   - 先判断一个问题能不能拆开。
   - 哪些部分可以独立运行，哪些部分必须先后依赖，哪些数据可以复制，哪些必须共享。

2. **调度与分配**
   - 把拆好的任务分配给可用执行单元。
   - 这些执行单元可以是 CPU 核心、GPU 线程块、NPU 推理单元，或者分布式节点。

3. **同步与通信**
   - 并行不是无限自由的，任务之间通常要交换数据、等待结果、保证顺序。
   - 常见手段包括锁、条件变量、barrier、队列、事件和显式拷贝。

4. **负载均衡**
   - 如果某些任务很重、某些很轻，就会出现“有人很忙、有人空闲”。
   - 需要通过任务切分、分片、批处理等方式尽量让资源利用均匀。

5. **存储和内存管理**
   - 并行性能常常不是算力不够，而是内存和通信在卡脖子。
   - 多线程共享内存会有竞争，GPU 要考虑显存和 host-device 传输，异构系统要考虑数据在哪一侧处理更划算。

### 1.4.3 并行代价：拆分、同步、通信与调试

并行不是白赚的，它有成本：

- 拆分任务有开销。
- 同步有开销。
- 通信有开销。
- 结果合并有开销。
- 调试更复杂。

所以并行是否值得，要看任务是否够大、依赖是否够少、并行粒度是否合适、通信是否比计算便宜。

### 1.4.4 一个直观例子：向量加法

- 串行做法：第 1 个元素算完，再算第 2 个，直到结束。
- 并行做法：把数组分成很多段，不同线程同时计算不同段。

如果数据足够大、拆分合理，并行版本通常会更快。
