# 教学实验：线程池与任务队列

> 对应章节：第4章。这个实验把“任务来了以后如何排队、分发、执行和收尾”拆成最小闭环，重点看线程池为什么比“每个任务新建一个线程”更稳。

## 实验目标

- 先理解任务队列、工作线程和等待/唤醒之间的关系。
- 再观察任务粒度、线程数和队列容量对吞吐的影响。
- 最后建立一个可复用的线程池骨架，为后面的 Host 调度与流水线实验做底座。

## 运行

```bash
make run
./task_pool 1048576 4096 4 128
```

参数含义：

- `n`：输入元素个数，默认 `1<<20`
- `chunk`：单个任务处理的元素数，默认 `4096`
- `workers`：工作线程数，默认按机器自动估算
- `repeat`：每个元素内部的重复计算次数，默认 `128`

## 文件结构

| 文件 | 说明 |
|------|------|
| `task_pool.c` | 线程池与有界任务队列实现 |
| `task_pool.h` | 公共声明 |
| `main.c` | 对比驱动：计时 + 校验 + 加速比报告 |
| `Makefile` | 仅需 pthread 即可构建 |

## 教学要点

- 这不是“线程越多越快”的实验，而是“任务怎么被组织起来”的实验。
- 线程池的关键不是线程本身，而是任务队列、等待/唤醒和关闭流程。
- 当 `chunk` 太小，调度开销会盖过计算收益；当 `chunk` 太大，负载均衡又会变差。
- 这个实验最适合和第4章正文一起读，把“任务生命周期”真正看见。

## 推荐观察

1. 固定输入规模，改变 `chunk`，看加速比如何变化。
2. 固定 `chunk`，改变 `workers`，看什么时候开始出现收益递减。
3. 把 `workers` 设为 1，观察线程池和串行路径是否完全一致。
4. 观察队列容量较小时的等待行为，理解生产者和消费者如何互相配合。

## 动手实验

1. 把 `repeat` 改小，观察“调度成本”是否变得更明显。
2. 把 `chunk` 改成 `256` / `16384`，比较任务粒度对效率的影响。
3. 把 `workers` 改为 `物理核心数 - 1` 和 `2 x 物理核心数`，比较过度订阅的效果。
