# 实战1：向量加法（CPU串行 vs OpenMP vs CUDA）

> 对应章节：第9.4节。这是教程的"入门旗舰示例"，演示同一问题在三种实现下的写法、统一计时口径与强制结果校验。

## 运行

```bash
make run            # 仅 CPU（串行 + OpenMP），无需 CUDA 工具链
make USE_CUDA=1 run # 含 CUDA 实现（需 NVIDIA GPU + nvcc）
./vec_add 33554432  # 自定义元素个数
```

## 文件结构

| 文件 | 说明 |
|------|------|
| `vec_add_serial.c` | 串行实现，作为结果校验的黄金参考 |
| `vec_add_openmp.c` | OpenMP 数据并行 |
| `vec_add_cuda.cu` | CUDA 实现，演示完整 Host↔Device 协同流程 |
| `main.c` | 对比驱动：计时 + 校验 + 加速比报告 |

复用 `../common/` 下的 `bench.h`（warmup + 多次取中位数）、`verify.h`（逐元素校验）、`cuda_helpers.cuh`（错误检查 + 设备侧计时）。

## ⚡️ 重要观察：为什么 OpenMP 不一定更快？

向量加法每个元素只做一次加法，却要读两个、写一个 float——**计算密度极低，是典型的内存带宽受限（memory-bound）问题**。在这种负载下：

- 多线程无法提升性能，因为瓶颈是内存带宽而非算力，加上线程调度开销，OpenMP 版甚至可能比串行更慢。
- GPU 的优势同样主要来自其更高的显存带宽，而非"核多"；且本例包含 H2D/D2H 传输，小数据量时传输开销可能盖过收益。

这正是第8章"计算密度决定是否上加速器"和第13章"带宽受限 vs 计算受限"的活教材。**矩阵乘（第9.6节）才是计算受限、能展现加速器威力的对照例子。**

## 动手实验

1. 改变 `n`，观察 CPU 与 GPU 的交叉点在哪里。
2. 用 `OMP_NUM_THREADS=1/2/4/8 ./vec_add` 观察线程数对带宽受限负载的（非）影响。
3. 用 `nvprof` / `nsys` 查看 CUDA 版的时间线，估算传输 vs 计算的占比。
